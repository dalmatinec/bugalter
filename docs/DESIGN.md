# Бизнес-логика и принятые решения

## Что согласовано с заказчиком

| Тема | Решение |
|---|---|
| Подразделения | Одна система; сотрудники, остатки, отчёты и права — раздельные. Оператор может работать в нескольких подразделениях |
| Виды работ | Данные, а не код: создаются, переименовываются, отключаются через бота (`/wt_add`, `/wt_off`…) |
| Тарифы | Индивидуальные и общие с переопределением; история; задним числом — только владелец или администратор с полными правами |
| Операции | Статусы: черновик → ожидает → подтверждено / отклонено / отменено. Повтор запроса не создаёт дубль |
| Повторы по заказу | Разрешены: один сотрудник может получить несколько одинаковых операций по одному заказу |
| Заказы | Живут только в группе: номер заказа — текстовая метка `#A-1052` в операции |
| Периоды | Общие для всех: два раза в месяц (1–N и N+1–конец, N настраивается) + выплаты по запросу |
| Валюта | Настраивается (`/set currency USD`), у каждой суммы хранится своя валюта |
| Премии | Выписываются и подписываются (`/bonus` → кнопка «Подписать») |
| Группа / личка | Группа — ввод и подтверждение операций, склад; личка — деньги, расчёты, отчёты. Суммы в группе скрыты |
| Получение товара | Выдача сотруднику идёт «в пути», получатель (или оператор) подтверждает; операторов уведомляют |
| Недостача | Не становится удержанием автоматически: расхождение → решение руководителя → документ удержания → подпись |
| Закрытый период | Не меняется. Исправления — в открытом периоде со ссылкой. Переоткрыть может только владелец с причиной |

## Значения по умолчанию, выбранные без явного ответа (меняются командой `/set`)

| Настройка | По умолчанию | Смысл |
|---|---|---|
| `currency` | USD | валюта новых тарифов и выплат |
| `rounding_mode` | HALF_UP | арифметическое округление каждой операции до минимальной единицы валюты |
| `timezone` | UTC | граница дня и периода — **задайте свой часовой пояс** |
| `payroll_split_day` | 15 | периоды 1–15 и 16–конец месяца |
| `group_show_amounts` | нет | суммы в группе не показываются |
| `allow_self_confirm` | да | автор может сам подтвердить свою запись (но никогда — запись в свою пользу) |
| `payout_requires_confirmation` | да | выплата проводится после отдельного подтверждения |
| `allow_negative_balance` | нет | выплата сверх заработанного запрещена |
| `deduction_requires_consent` | нет | штраф/удержание проводится после подписи; при «да» — ещё и после согласия сотрудника |

Жёсткие правила, которые не отключаются: никто, кроме владельца, не подтверждает и не подписывает записи
в свою пользу и не регистрирует выплату самому себе; права нельзя выдать больше, чем есть у выдающего;
роль владельца выдаёт только владелец; последнего владельца нельзя лишить роли.

## Как считаются деньги

* Сумма операции = количество × ставка (`per_unit`) или ставка (`fixed`), округляется **сразу** по правилам
  вида работ/валюты. Поэтому сумма строк расшифровки всегда равна итогу.
* Ставка выбирается на **дату выполнения** работы: сотрудник+подразделение > сотрудник > подразделение > общая;
  внутри уровня — с самой поздней датой начала. Нет ставки — операцию провести нельзя (не 0).
* Ставка копируется в операцию. Новый тариф не меняет подтверждённые операции; тариф задним числом
  пересчитывает только черновики и ожидающие подтверждения.
* Все деньги сотрудника — журнал `ledger_entries` (+ компания должна, − сотрудник должен).
  Начисление появляется только при подтверждении операции / подписи документа / подтверждении выплаты.
  Уникальный ключ «документ + тип проводки» исключает двойное начисление даже при одновременных нажатиях.
* Отмена проведённого = сторно в **открытом** периоде с исходной датой. Закрытый период триггер БД не пускает.
* «Доступно к выплате» = остаток − зарегистрированные, но не подтверждённые выплаты − открытые запросы.
* Закрытие периода фиксирует итоги каждого сотрудника (вход, начислено, удержано, корректировки, выплачено,
  остаток) + хеш проводок. Переоткрытие и повторное закрытие создают новую версию, старая сохраняется.

## Склад

* Каждое движение — «откуда → куда». Поставщик, клиенты, списание, недостача, излишек — условные места.
* Реальные места (склад подразделения, сотрудник, «в пути») не могут уйти в минус — проверка в коде и CHECK в БД.
* Количество вводится в любой единице товара (`уп`), хранится в базовой (`кг`) с проверкой точности.
* Инвентаризация сравнивает учёт с фактом; разница уходит в «недостачу»/«излишек» и открывает расхождение.
* `verify_balances()` сверяет текущие остатки с журналом движений.

## Защита от ошибок

| Риск | Защита |
|---|---|
| Двойное нажатие / повтор сообщения | `idempotency_key` из chat_id+message_id или ключ мастера; уникальные индексы |
| Два руководителя подтверждают одновременно | `SELECT … FOR UPDATE` + уникальность проводки по документу |
| Правка проведённых записей | Триггеры: журналы только добавляются; у проведённых операций и документов нельзя менять сумму/сотрудника |
| Запись в закрытый период | Триггер на `ledger_entries` (с блокировкой строки периода) |
| Отрицательный остаток товара | Проверка с блокировкой + CHECK в БД |
| Float-ошибки в деньгах | Только Decimal/NUMERIC, ввод с лишними знаками отклоняется, а не округляется |
| Сообщение «готово», а транзакция откатилась | Ответы отправляются только после COMMIT |
| Утечка зарплат в группе | Денежные команды только в личке; суммы в групповых карточках скрыты |
| Сбой | Пользователь получает код ошибки, владельцы — уведомление, данные не меняются |

Ограничение: человек с доступом владельца базы данных на сервере может отключить триггеры.
Защита от него — резервные копии вне сервера и отдельный пользователь БД для приложения (см. «Дальше»).

## Открытые вопросы

1. Страна, форма занятости и правовые ограничения удержаний (лимит удержания от выплаты, обязательность согласия).
   Сейчас есть настройка `deduction_requires_consent`; лимит в процентах не реализован.
2. Выплата сверх заработанного (аванс в долг), лимиты и порядок погашения долга. Сейчас запрещено; долг
   (отрицательный остаток) просто переносится в следующий период.
3. Себестоимость по партиям — заготовка в схеме (`batches`, `batch_id`), в расчётах не используется.
4. По какой цене удерживать стоимость товара — вводится руководителем в решении по расхождению с основанием.
5. Формулы сложнее «количество × ставка» и «фикс» (ступенчатые шкалы, проценты, коэффициенты) — не реализованы.
6. Веб-панель администратора — сейчас администрирование командами в личке.

## Дальше (технически)

* Отдельные пользователи БД: владелец схемы для миграций и пользователь приложения без права `ALTER/TRUNCATE`.
* Redis для состояния мастеров (сейчас в памяти: при перезапуске незаконченный мастер нужно начать заново;
  черновики и операции не теряются).
* Ежедневная сводка в группу, напоминания о неподтверждённых операциях.
